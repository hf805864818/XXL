# PetDFY T3 完整化实施方案

**基线**：`源码/源码完整版.tar.zip`（`0.1.8-editable`，137 源文件 / 41,245 行 / 3 个 dylib）
**目标终态**：一套能编译、能装、能渲染 **15 套服装** + 能播 **素材 A 的 116 组动作** 与 **小白龙 12 组动作**，并把 T1/T2 的运维与安全能力补齐的工程。
**编写日期**：2026-11-24　**口径**：`Observed` 静态实测 / `NOT RUN` 未运行验证

---

## 0. 先明确三条判断

1. **T3 是"接口最全、编排未接完"的工程**，不是"能跑的工程"。方法级 100% 覆盖，证据保真度 68%，构建脚本存在硬语法错误 —— 说明它从未真正 `make` 过。
2. **服装和动作是两条不同的技术路线**，必须分开做，不能混：
   - 服装 = 骨骼 rig + 贴图替换（T3 已有 90%，缺模型注入）
   - 动作 = 整帧位图序列（T3 **完全没有**，要新建引擎）
3. **小白龙不是"一套服装"**。实测该包只有 `frames/`（12 组）+ `clips.plist` + `catalog.plist` + `mascot.png` + `sounds/`，**没有 `originals/outfits/`、没有 `model.json`**。它是"另一个角色"，需要在 T3 里新增**角色层（Character）**，而不是塞进服装白名单。

## 2. 阶段一（e1）：让 T3 编译通过并出包（3 个改动点）

### 2.1 修 Makefile（必须先做）

```diff
-//  Makefile — PetDFY 可编辑源码工程（Theos）
+#   Makefile — PetDFY 可编辑源码工程（Theos）
```

三处要一起改：

| 项 | 现在 | 改成 | 原因 |
|---|---|---|---|
| 注释符 | `//` | `#` | Makefile 语法 |
| `TARGET` | `iphone:clang:latest:14.0` | `iphone:clang:latest:16.0` | 原版 `Depends: firmware (>= 16.0)`；`RootHide` 环境也要求 16+ |
| `PetDFY_LIBRARIES` | `substrate` | `substrate`（普通越狱）/ 空 + `-Wl,-undefined,dynamic_lookup`（RootHide） | RootHide 无 libsubstrate |

顺带要确认：`PetDFY_FILES = $(shell find src/Core src/Sources src/Ext -name '*.m')` —— 不含 `src/Aux`（正确，两个辅助单独编）。

### 2.2 建 `assets_src/`

```bash
mkdir -p assets_src
cp -R "<素材A>/originals" assets_src/
cp -R "<素材A>/live"      assets_src/
cp "<T3>/PDLayout.json"   assets_src/   2>/dev/null || true
```

> 素材 A 的 `originals/`（1,057 文件 / 23 MB）+ `live/model.json`（111 KB，15 个 model）就是 T3 需要的结构。
> 若嫌大，先只放 `originals/tex`、`originals/feat`、`originals/outfits/maid` 做首次跑通，后面再补全。

### 2.3 出包

```bash
export THEOS=~/theos
make clean all        # 期望产出 3 个 dylib：PetDFY / PDFYEnhance / PDFYSecurity
make package          # 期望产出 packages/*.deb
```

## 3. 阶段二（e2 / e3）：让渲染真的出画面（先单套，再 15 套）

### 3.1 修模型注入（B2 + B3，核心一步）

在 `WNLiveRig.m` 的 `// 115 deformersDirty = YES;` 之后、`return self;` **之前**插入：

```objc
NSData *md = [NSData dataWithContentsOfURL:
              [[self resourceURL] URLByAppendingPathComponent:@"live/model.json"]];
if (md.length) {
    id json = [NSJSONSerialization JSONObjectWithData:md options:0 error:NULL];
    id models = [json isKindOfClass:[NSDictionary class]] ? json[@"models"] : nil;
    NSDictionary *chosen = nil;
    if ([models isKindOfClass:[NSDictionary class]]) {
        chosen = models[_outfit] ?: models[@"maid"];          // 字典：15 套按 id 直取
    } else if ([models isKindOfClass:[NSArray class]]) {
        NSPredicate *p = [NSPredicate predicateWithFormat:@"id == %@", _outfit];
        chosen = [[(NSArray *)models filteredArrayUsingPredicate:p] firstObject]
                 ?: [(NSArray *)models firstObject];
    }
    if ([chosen isKindOfClass:[NSDictionary class]]) {
        _model = chosen;          // parts / deformers / view 全在里面
        _sourceModel = chosen;    // WNPainter 侧要用
    }
}
deformersDirty = YES;
```

### 3.2 打通 outfit 传递（B4 + B5）

```objc
// WNLiveRig.m:104
- _outfit = @"maid";
+ _outfit = [scheme length] ? @"maid" : @"maid";   // 先占位
+ // 由 WNRenderer 在 initWithResourceURL 之后显式赋值：
+ //   rig.outfit = PDAIPreference(@"Outfit", @"maid");
```

更稳的做法是给 `initWithResourceURL:scheme:seed:freeGround:` 增加 `outfit:` 参数，`WNRenderer.m:851` 调用处一起改，避免"先建后设"导致 `_model` 取错套。

```objc
- renderer.liveRig.outfit = outfit;
+ [renderer resetLiveWithScheme:scheme freeGround:YES];   // 重建 rig，重新注入 model
```

## 4. 阶段三（e4）：帧动画引擎

### 4.1 架构决策：双渲染源，互斥切换

```
                ┌────────────────────────────┐
   骨骼动画   →  WNMotion → WNLiveRig → WNPainter → Metal → 屏
   （内置动作）  └────────────────────────────┘
                ┌────────────────────────────┐
   帧动画     →  PDDirectorFrame → 整帧 webp → CGImage → 同一 MTL 纹理 → 屏
   （素材包）    └────────────────────────────┘
```

规则：任一时刻只有一路在画。帧动画播放时 `[rig setPaused:YES]`（或暂停 `renderBuildingMesh:`），结束后恢复骨骼渲染与交互。

### 4.2 移植 T1 的播放器

| 动作 | 文件 |
|---|---|
| 拷入 | `Core/PDFramePlayer.h/.m`（T1，7004 B）→ 放到 `src/Ext/PDDirectorFramePlayer.{h,m}` |
| 数据源适配 | T1 读 `clips.plist`（plist）；T3 惯用 JSON。**两种都支持**：先 `NSPropertyListSerialization`，失败再 `NSJSONSerialization` |
| 路径适配 | 素材根的解析复用 `PDTextureResolver`，不要另起一套 |
| 渲染目标 | 不要新建 `MTKView`；把 CGImage 写进 `WNRenderer` 已有的纹理缓存，避免两个图层抢窗口 |
| Makefile | 若同时要 T1 的 `PDZip`，加 `-lz` |

### 4.3 动作入口（两套素材共用一个引擎）

```
素材 A：116 组，帧数 15–31，432×360，frameMs=168（抽帧后）
小白龙：12 组，帧数 121–361，432×360，frameMs=42（原速）
```

入口设计：

| 触发 | 行为 |
|---|---|
| 双击（`DoubleTapAction=clip`） | 随机播一个「点击类」动作（A: `poke_*` / B: `tsundere`/`wave`） |
| 长按菜单 →「动作」 | 按 `catalog.plist` 的 14 类 / 4 类分组列出，点选播放 |
| 设置页新增「动作库」页 | 列出全部组 + 帧数 + 时长，可试播（可选，P2） |

### 4.4 小白龙 = 角色层（不是服装）

新增一个轻量层，别改 outfit 语义：

```
角色（character）        = 一套完整的渲染方案
  ├─ kind = "rig"        → 骨骼 + originals/ + model.json      （现有 15 套）
  └─ kind = "frames"     → frames/ + clips.plist + mascot.png  （小白龙）
```

- 存储：`/var/mobile/Library/Application Support/PetDFY/Characters/<id>/`，各角色一个目录
- 切换：设置页新增「角色」分页（`PSLinkListCell`，动态读目录；不重编 `PetDFYPrefs` 也可，因为它是动态 plist）
- 小白龙缺 `model.json` → 走 `kind=frames`，**不参与骨骼渲染**，也不进「服装」列表

### 4.5 验收判据（e4）

| # | 判据 |
|---|---|
| C1 | A 抽 3 组（`idle` 类 / `fest_xmas` / `work_code`）能完整播完，不卡顿、不掉帧 |
| C2 | 小白龙抽 3 组（`idle` 145 帧 / `astra_form` 361 帧 / `fire_breath` 241 帧）能播 |
| C3 | 播放中点击/拖动有响应，能打断并回待机 |
| C4 | 退出播放后骨骼渲染恢复，30 秒内无内存持续增长（15 套 + 3,437 帧全量缓存约 100 MB，要确认不 OOM） |
| C5 | 切换角色/服装后不需要重启 SpringBoard |

## 7. 风险与回退

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 阶段二改了 `_model` 后仍不出画面（还原层还有别的断点） | 中 | 阻塞全部 | 先只跑 `maid` + 加 `PDLogger`，用日志定位 `parts`/`deformers` 哪一步空 |
| 15 套贴图总量 ~24 MB，116 组帧 ~81 MB，全量缓存 OOM | 中 | 崩 SpringBoard | 纹理 LRU、帧动画按需加载、只缓存当前动作前后各 30 帧 |
| 帧动画与骨骼渲染抢 GPU/画面 | 中 | 花屏闪烁 | 严格互斥 + 同一 MTL 纹理队列 |
| 双注入 `com.apple.Preferences` 导致设置页闪退 | 中 | 无法改设置 | 诊断面板做成可选（单独一个 deb 变体） |
| RootHide 下 `substrate` 链接失败 | 高 | 装不上 | 用 `dynamic_lookup`，或改用 RootHide 的 libhooker |
| iOS 版本差异（16 vs 17 vs 18） | 中 | 部分 API 不存在 | `TARGET` 定 16.0，运行期做 `respondsToSelector` 保护 |
| 找不到原始 `assets_src` | 高 | 素材不全 | 直接用素材 A 替代；保留 `asset-manifest.json` 校验 |

**回退**：所有阶段都保留原版 `com.ojbkclub.petdfy_0.1.7` deb 作为 baseline（已在 `小白龙素材/P1.5…/baseline/`），任何阶段装挂了都能 `dpkg -i` 回退。

## 13. 三越狱兼容（目标 iOS 17.0：Relaxin / RootHide / Dopamine）

### 13.1 三种越狱的差异

| 越狱 | 类型 | 安装根 | 关键点 |
|---|---|---|---|
| Dopamine | rootless | `/var/jb` | 路径前缀 `/var/jb`，依赖 ellekit |
| RootHide | roothide | `/var/containers/Bundle/Application/.jbroot-*`（随机名） | 隐藏根，必须运行时探测 |
| Relaxin | 待实测确认 | 见 14.4 | 不依赖具体定义也能覆盖 |

### 13.2 不依赖定义的通用做法（XiaoXiong 已实现）

一个 deb + 智能 `postinst`：

```sh
# 1) 找安装根：先 /var/jb，再 /
JB=""
for base in /var/jb /; do
    [ -d "$base/Library/MobileSubstrate/DynamicLibraries" ] && { JB="$base"; break; }
done

# 2) 扫 roothide 的隐藏根
for candidate in /var/containers/Bundle/Application/.jbroot-* \
                 /rootfs/var/containers/Bundle/Application/.jbroot-*; do
    [ -d "$candidate/Library" ] || continue
    COUNT=$((COUNT+1)); CANDS="$CANDS $candidate"
done

# 3) 多个候选时不盲选：只认已经装有我们 dylib 的那个，否则拒绝安装
if [ "$COUNT" -gt 1 ] && [ -z "$REAL" ]; then
    echo '检测到多个 jbroot，无法安全确定安装目标。'; exit 1
fi
```

配套三条：

| 项 | 做法 |
|---|---|
| 依赖声明 | `Depends: firmware (>= 16.0), mobilesubstrate | ellekit | libhooker` |
| 日志 | 私有目录 `0700`，文件 `0600`，不写固定 `/tmp`（防符号链接截断） |
| 失败处理 | `set +e` + 失败计数，不掩盖、不假装成功 |

### 13.3 dylib 内的路径改造（T3 必须做）

T3 里现有硬编码：

| 位置 | 现在 | 应改为 |
|---|---|---|
| `PDPreferences` / `PDAssetManager` | `/Library/...`、`/var/mobile/...` | 统一走 `jbroot()` 前缀函数 |
| 素材根 | `Application Support/PetDFY` | 用户数据在 `/var/mobile` 下（rootless 不变），但**安装路径**要加 jbroot |
| 注入过滤器 | `/Library/MobileSubstrate/DynamicLibraries` | 打包后由 postinst 搬到探测到的根 |

推荐实现（与 XiaoXiong 一致）：

```objc
static NSString *PDJBRoot(void) {
    static NSString *root = nil;
    if (root) return root;
    if ([[NSFileManager defaultManager] fileExistsAtPath:@"/var/jb/usr/lib"]) root = @"/var/jb";
    else root = @"";
    return root;
}
```

### 13.4 Relaxin 的确认方式

设备上跑一条命令即可（不需要查资料）：

```sh
ls -d /var/jb /var/containers/Bundle/Application/.jbroot-* 2>/dev/null
```

- 有 `/var/jb` → rootless 类，按 Dopamine 处理
- 只有 `.jbroot-*` → roothide 类，按 RootHide 处理
- 都没有 → rootful（`/` 直接可写），按传统越狱处理

§13.2 的 postinst 三种都覆盖，所以**不需要提前确定 Relaxin 属于哪类**。

| F1 | 三种越狱各装一次，`dpkg -i` 无错误 |

## 14. 设置页能力边界（结论见 §15）

### 14.1 能力边界

| | 保持原版（846,688 B，动态读 plist） | 重编（需要 Prefs 源码） |
|---|---|---|
| 分组 / 开关 / 列表 / 滑块 / 子页 | ✅ | ✅ |
| 静态选项（写死 `validValues`） | ✅ | ✅ |
| **动态列表**（扫目录生成） | ⚠️ 只能在安装时静态化 | ✅ 运行时直接扫 |
| **缩略图网格 / 素材预览** | ❌ | ✅ |
| **实时诊断面板 / 按钮** | ❌ | ✅ |
| 与主 dylib 共享头文件 | ❌（只靠偏好域 + key） | ✅ |
| 改动成本 | 低（改 plist，可热更新） | 高（重编 + 签名 + 版本对齐） |

### 14.2 对二开的影响（直接回答）

| 你想做的事 | 保持原版够不够 |
|---|---|
| 加「角色」分页（小白龙） | **够，但要折中**：安装时扫 `Characters/` 目录，把 id 写进 plist 的 `validValues`。新增角色要重装或重跑脚本才出现 |
| 加「动作库」分页（116 组，带预览） | **不够**，需要缩略图与分组交互 → 必须重编 |
| 加实时日志/诊断面板 | **不够** → 必须重编 |
| 改文案、调默认值、加开关 | 够 |

### 14.3 三档折中

| 档 | 做法 | 成本 | 能加什么 |
|---|---|---|---|
| 1 | 纯 plist | 0 | 静态选项、开关、滑块 |
| 2 | plist + 安装期静态化（postinst 扫目录写 validValues） | 低 | 「角色」分页（无缩略图） |
| 3 | 重编 Prefs | 中 | 全部，含缩略图网格、诊断面板 |

> **关键差异**：XiaoXiong 线自带 Prefs 源码（`DFYPrefs.m` 62 KB），要重编 Prefs 有现成材料；
> T3 线只有二进制，重编等于再逆向一遍设置页。
> 但 T3 选了第三条路 —— **运行时面板**（见 §15），所以这条差异不再是选线的决定因素。

## 15. 设置页二进制：解剖结果与运行时面板路线

### 15.1 这个二进制到底是什么

| 项 | 实测值 |
|---|---|
| 路径 | `layout/Library/PreferenceBundles/PetDFYPrefs.bundle/PetDFYPrefs` |
| 大小 | 846,688 B |
| 架构 | **fat：arm64 + arm64e**（两个 slice，各自独立签名） |
| 类型 | Objective-C，**无 Swift 段**、无壳、无加固 |
| 自定义类 | **18 个**（`__objc_classlist` 18 指针） |
| 方法 | `__objc_methlist` 439 条 / selector 引用 566 个 |
| 系统类引用 | 62 个（`PSListController` 12 次、`UITableView` 100 次） |
| 内嵌文案 | **`__ustring` 100,428 字节**（UTF-16，含大量 AI 工具定义 JSON） |
| 符号 | 仅 293 个导出符号（strip 过） |

**作用**：由 PreferenceLoader 加载进 `Preferences` 进程，画「设置 → 大肥鱼」的整个界面与逻辑（分组、开关、列表、滑块、四个子页、下载页、导入交互）。

**为什么 T3 没有它的源码**：T3 的逆向目标只有 `PetDFY.dylib` 与两个辅助 dylib，Preferences bundle 是原样搬运，从未逆向。

### 15.2 能不能完整重编：能，但有三道坎

| 坎 | 风险 | 严重度 |
|---|---|---|
| 私有框架 | `PSListController`/`PSViewController`/`PSSpecifier` 是 Apple 私有，头文件要自建，ABI 错一个字段即崩 | 高 |
| 签名与注入 | Preferences 进程要求正确签名。历史事故：0.0.4 版改名后未重算 CodeDirectory → **设置页点不进去** | 高 |
| 偏好键契约 | 18 个类读写几十个 `CFPreferences` key，必须与主 dylib 完全一致 | 中 |

**隐性风险**：设置页坏掉的后果比桌宠不显示更严重 —— 用户失去唯一可改配置的入口，只能卸载重装。

工作量估计：18 类 / 439 方法 + 100 KB 文案提取，按 T3 已有工具链约 **1–2 周**，且需真机验证。

### 15.3 决策：不重编，走运行时面板（D-13）

原作者在 `Ext/PDHairTintPanel.h` 里已经写明了这条路线：

> 为什么做在运行时而不是设置 App 里：设置 App 的偏好包是编译好的二进制，改它要重编 846 KB 的 `PetDFYPrefs`；而这个面板挂在桌宠自己的窗口上，源码完全在我们手里……设置 App 里同样有发色分页，两处写的是同一组 CFPreferences 键，互相看得见。

延续这个模式：

| 面板 | 对应需求 | 参考实现 |
|---|---|---|
| `PDHairTintPanel` | 发色 | **已存在**（UIView + `presentInWindow:`） |
| `PDCharacterPanel`（新） | 角色切换（小白龙） | 抄 `PDHairTintPanel` 结构 |
| `PDClipPanel`（新） | 116 组动作浏览/试播 | 抄 + `UICollectionView` |
| `PDAssetPanel`（新） | 素材导入/删除/预览 | 抄 + `PDZip` |
| `PDModelPanel`（新） | 模型列表刷新/选择 | 抄 |
| 长按菜单 | 三个新入口 | `hoverActions` 数组 + 分支 |

设置页只保留 plist 能表达的静态项（分组、开关、静态列表、滑块），与面板共享同一组 `CFPreferences` 键，双向可见。

### 15.4 什么情况下才回头重编设置页

| 场景 | 处理 |
|---|---|
| 加「角色」「动作库」「素材管理」入口 | 面板做，不重编 |
| 改分组顺序/文案/默认值 | 改 plist，不重编 |

## 18. 打包策略与 deb 体积（2026-11-24 定）

### 18.1 现状：33 MB 从哪来

| 内容 | 大小 | 文件数 |
|---|---:|---:|
| 15 套服装贴图（`originals/outfits/<id>/`） | ~17 MB | 306 PNG |
| 7 套配色（`originals/schemes/<name>/tex+feat`） | ~12 MB | 385 PNG |
| 扁平贴图 + 表情（`originals/tex`、`feat`） | ~4 MB | 352 PNG |
| 程序 + plist + `petdfy-voice` | ~6 MB | 27 文件 |
| **压缩后合计** | **33 MB** | 1,085 文件 |

原始素材 114 MB → xz 压缩率 29%。**原版 deb 只有 2.2 MB**，因为它把素材做成"设置页导入 ZIP"的外置设计（0.1.7 = 2,313,732 B）。

### 18.2 已采用方案 C：拆成两个 deb（2026-11-24 定）

原版设计本来就是"程序 + 素材"分离，现在正式照这个结构走：

| 包 | 内容 | 大小 | 装法 |
|---|---|---:|---|
| **程序包** `com.ojbkclub.petdfy` | 三个 dylib + plist + 偏好包 + `petdfy-voice` | **2.2 MB** | 先装 |
| **素材包** `com.ojbkclub.petdfy.assets` | `originals/`（15 套 + 7 配色 + 表情）+ `live/model.json` | **31.3 MB** | 后装（`Depends: com.ojbkclub.petdfy (>= 0.1.9)`） |

### 18.3 为什么用"双 deb"而不是原版的"ZIP 导入"

| 方式 | 可行性 | 说明 |
|---|---|---|
| 原版：设置页导入 ZIP | ❌ 不可靠 | 导入器在二进制里，T3 源码**没有还原**（`PDAssetManager.m` 只有下载逻辑，9.4 KB，无 unzip/manifest 解析） |
| T1：内置 PDZip + PDFindAssetRoot | ⚠️ 要移植 | T1 有完整实现，但那是另一条线的代码 |
| **本方案：双 deb** | ✅ 最稳 | 用 dpkg 装，不依赖任何导入器；素材升级只需重装素材包 |

**代价**：素材包不能"发个 ZIP 让用户自己导入"，但公众号/群里发两个 deb 也一样方便。

### 18.4 包结构（实测）

```
PetDFY_0.1.9_prog_iphoneos-arm64e.deb        2.2 MB · 55 成员（22 目录 + 33 文件）
PetDFY-Assets_1.3.0_iphoneos-arm64e.deb     31.3 MB · 1104 成员（46 目录 + 1058 文件）
```

> **注意**：打包必须包含 **目录条目**（`TarInfo(type=DIRTYPE)`）。纯文件 tar 会让 dpkg 在新建目录时失败：
> `unable to create '.../manifest.example.json.dpkg-new': No such file or directory`

### 18.5 为什么不一次打全（历史）

- e2/e3 会反复替换 `assets_src` 里的贴图，拆包后每次都要重打两个产物；
- 33 MB 对本地安装无感（`dpkg -i` 一两秒）；
- 真正影响体验的是"装完有没有角色"，不是"包多大"。

## 19. 素材 ZIP 导入方案（待开发，等主 dylib 能编译）

### 19.1 为什么要 ZIP 导入

素材会持续变大（15 套 → 更多服装、116+ 动作、表情部件），全量 deb 会越来越重。
**ZIP 导入的价值**：用户只下"增量素材包"，不用重装整个 deb；素材可以单独分发、单独回滚。

### 19.2 与双 deb 的关系（不是替代）

| 场景 | 用哪种 |
|---|---|
| 首次安装 | **程序 deb + 素材 deb**（dpkg 装，最稳） |
| 素材更新（加服装 / 加动作 / 修图） | **ZIP 导入**（走设置页，不动 deb） |
| 分享给别人 | 三个文件都行：程序 deb + 素材 deb + 可选增量 ZIP |

### 19.3 ZIP 结构（导入器契约）

```
PetDFY-Assets-<version>.zip
├── manifest.json          { schema:2, kind:"layered", version:"1.3.0",
│                            fileCount:1058, totalBytes:...
│                            files: { "originals/tex/x.png":"<sha256>", ... } }
├── originals/
│   ├── tex/  feat/  outfits/<id>/  schemes/<name>/  thumbs/
│   └── model.json  figure.json
└── live/model.json
```

**三条硬要求**：
1. 根目录必须有 `manifest.json`（导入器靠它校验，缺了就静默跳过 —— 素材 A 的 `README-FIX.md` 踩过这个坑）
2. 路径用 `/`，不要带顶层目录（或在导入器里做"自动定位素材根"）
3. 每个文件的 sha256 必须与 manifest 一致

### 19.4 导入流程（5 步）

```
① 用户在「设置 → 大肥鱼 → 下载」点「导入 ZIP」
   └─ UIDocumentPickerViewController 选文件（需 UTType 声明 zip）
② 复制到临时目录  /var/mobile/Library/Application Support/PetDFY/.import/<uuid>/
③ 解压（内置 inflate，不依赖 /usr/bin/unzip）
   └─ 失败时回退系统 unzip，两者都失败 → 写 failed 状态并报错
④ 定位素材根（先查目录本身，再扫一级子目录找 live/model.json）
   └─ 校验 manifest.sha256 + live/model.json + clips.plist（可选）
⑤ 原子替换到 /var/mobile/Library/Application Support/PetDFY.bundle/
   └─ 旧目录改名 .bak → 新目录 rename → 成功后删 .bak
   └─ 写 AssetDownloadStatus = ready → 触发 discardAssetViews + start（免重启）
```

### 19.5 移植清单（从 T1 借）

| 模块 | T1 文件 | 规模 | 作用 |
|---|---|---|---|
| ZIP 解压 | `Core/PDZip.{h,m}` | 11 KB | zlib inflate，支持 store/deflate、ZIP64、跳过 `__MACOSX` |
| 导入链路 | `Core/PDOverlayController.m` 里的 `pd_pollAssetImports` / `PDFindAssetRoot` / `PDInstallCombinedArchive` | 约 400 行 | 轮询、定位素材根、原子替换、状态回写 |
| 落盘日志 | `Core/PDLogger.{h,m}` | 4 KB | 导入全链路打点，排查用 |
| 诊断面板 | `Core/PDPreferenceDiagnostics.{h,m}` | 10 KB | 可选，设置页内嵌状态显示 |

**依赖**：`Makefile` 加 `-lz`（PDZip 用 zlib）。

### 19.6 开发顺序（关键）

```
e1 主 dylib 能编译（未完成，卡在 PDOverlayController 等文件）
  ↓
e4 帧动画（PDClipPlayer）
  ↓
e5 ZIP 导入（本文档 §19.4 的流程）
  ↓
e7 面板（PDAssetPanel 里放「导入 ZIP」按钮）
```

**为什么 ZIP 导入排在后面**：它要改 dylib 代码（加 UIDocumentPicker、解压、原子替换），
而 dylib 现在编译不过 —— 先有能编的 dylib，才谈得上加功能。

### 19.7 验收判据

| # | 判据 |
|---|---|
| 1 | 选一个含 `manifest.json` 的 ZIP，导入后设置页显示「已就绪」 |
| 2 | 导入后**免重启**出现新素材（`discardAssetViews + start`） |
| 3 | 导入中途断电/取消，旧素材完好（原子替换） |
| 4 | 只有 `assetbridge/manifest.json` 没有根 `manifest.json` 的包，被明确拒绝并提示 |
| 5 | 导入后的素材目录与 manifest 的 sha256 逐条一致 |
