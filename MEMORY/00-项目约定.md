# 00 · 项目约定（三条铁律）

> 定于 2026-11-24。改动这三条之前先读 `01-决策记录.md` 的 D-8。

---

## 铁律 1：代码变更才编译，文档变更不触发

**实现位置**：`.github/workflows/build.yml` 的 `on.push.paths-ignore`

```yaml
paths-ignore:
  - '**.md'
  - 'docs/**'
  - 'MEMORY/**'
  - '.gitignore'
  - '.gitattributes'
```

| 改动 | 是否触发编译 |
|---|---|
| `src/**`、`layout/**`、`assets_src/**` | ✅ 触发 |
| `Makefile`、`control` | ✅ 触发 |
| `.github/workflows/build.yml` | ✅ 触发 |
| 任何 `.md` | ❌ 不触发 |
| `docs/**`、`MEMORY/**` | ❌ 不触发 |

**两个附带效果（有意为之）**：

1. CI 自动回写 `MEMORY/03-构建日志.md` 后提交，不会自激触发下一轮构建；
2. 改文档、写方案、补记忆点，都不浪费 Actions 分钟数。

**例外处理**：如果只想验证编译而不改代码，去 Actions 页点 **Run workflow**（`workflow_dispatch`）。

## 铁律 2：每次编译自动递增版本号

**实现位置**：`.github/workflows/build.yml` 的 `Compute version` 步骤

规则：

```
最终版本 = control 里的 base 版本 + "+build.NNN"
例：0.1.8-e1 + build.042 → 0.1.8-e1+build.042
```

| 项 | 谁维护 | 说明 |
|---|---|---|
| `base`（如 `0.1.8-e1`） | **人** | 一个阶段一个 base，改 `control` 里的 `Version:` 即可 |
| `build.NNN` | **CI 自动** | 取 `github.run_number`，三位补零，只增不减 |
| deb 文件名 | theos 自动 | `PetDFY_0.1.8-e1+build.042_iphoneos-arm64e.deb` |

**为什么这样设计**：版本号要能回答两个问题 ——「这是哪个阶段」和「这是第几次构建」。
纯语义版本（e1/e2）答不了第二个，纯流水号答不了第一个。

**怎么查某次构建**：`MEMORY/03-构建日志.md` 有一行对应记录（含 commit、版本、架构、SHA256 前 16 位）。

**注意**：CI 只在**工作区**改 `control`，不回写仓库 —— 所以仓库里的 `control` 永远是你手写的 base 版本，不会被 CI 弄脏。

## 铁律 3：每次推送都要补记忆点

**分两层，别混**：

### 3.1 机械记录（CI 自动，不用你管）

每次构建结束，CI 往 `MEMORY/03-构建日志.md` 追加一行：

```
| #42 | 2026-11-24 07:10 UTC | `a1b2c3d` | e2: inject model.json | `0.1.8-e1+build.042` | iphoneos-arm64e | ✅ | `5de54bdb279c32d4` |
```

失败也记（`❌`），因为失败本身是信息。然后 CI 用 `[skip ci]` 提交回仓库，失败不阻塞产物。

### 3.2 语义记录（人写，必须写）

推送前在对应文件补一句**「这一步做完了什么」**，格式固定三行：

```markdown
### e2 · 模型注入（2026-11-24）
- 做了什么：在 WNLiveRig init 返回前读 live/model.json，注入 _model/_sourceModel
- 判据：日志出现 `model injected: outfit=maid parts=34`，桌面出现角色
- 下一步：15 套白名单 + 逐套验收
```

写到哪：

| 内容 | 文件 |
|---|---|
| 阶段完成 / 判据通过 | `02-阶段进度.md` |
| 方案改动 / 新决定 | `01-决策记录.md` |
| 新踩的坑 | `04-已知问题.md` |

**判据必须可观察**（日志行 / 文件名 / 命令输出），不许写「应该可以了」。
